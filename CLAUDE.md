# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Piece is (v3)

A mobile-only social platform for AI-generated **female erotica**. Creators publish **worlds** (lore + characters) with curated **collections** of **scenes**; readers browse a public feed, tap a world, tap a scene, tap Generate, and read the streamed **story**. Stories are always private.

Think of the user base as ~99% readers, ~1% creators. The core path is the laziest one possible: browse → tap → generate → read. Favor reader convenience and UI/copy/consistency fixes over restructuring flows. Everything is explicit by design, so there is no content rating.

**Curated, not open.** Readers walk into strange worlds the way they'd walk into a bookstore: they come for a theme or a pairing dynamic, so what they play has to be guided and intentional. The author curates everything — collections, and the scenes in them, in the author's order; readers don't write scenes, and steer only inside a story (Expand / Continue with a direction). Scenes are the author's, edited or deleted freely; a reader's saved story of a scene that has since changed is simply **outdated**. v3 deliberately dropped v2's world versions/checkouts, scene clusters and versions, reader-written scenes, taste profiles and likes, world additions, chat, and example worlds. Don't reintroduce them. Collection prerequisites (a collection opening only once a reader has played one from another) are planned for Phase 2, not built.

## Runtime & commands

Bun is the runtime for both server and tooling (not Node). There is **no test suite and no lint config** — type-checking is the verification gate.

```bash
bun run dev          # server (:3001) + Vite client (:5173) concurrently
bun run dev:server   # Hono API only, hot-reloaded, :3001
bun run dev:client   # Vite only, proxies /api -> 127.0.0.1:3001
bun run build        # vite build -> dist/
bunx tsc --noEmit    # type check (the only automated check; run before declaring done)
bun run start        # production: NODE_ENV=production, serves dist/ + API on :3000
```

There are no one-off data scripts: the schema lives in `server/db.ts` and is created on startup.

Requires `OPENROUTER_API_KEY` in the environment for generation. **v3 runs on its own database: `V3_DB_PATH`, default `./piece-v3.db`.** It deliberately ignores `DB_PATH` / `DEV_DB_PATH` — those point at the v2 databases (`migrated.db`, `prod.db`, `piece.db`), and v3's `CREATE TABLE IF NOT EXISTS` would silently keep v2's tables of the same names. v3 started empty; no v2 data is carried over. A Fly deploy needs `V3_DB_PATH` set to a file on the `/data` volume.

## Architecture

**Stack:** Bun + Hono API, React 19 + React Router 7 (data router) + TanStack Query client, Tailwind v4, Drizzle ORM over `bun:sqlite`. `@/*` aliases `src/*` (configured in both `vite.config.ts` and `tsconfig.json`). A few modules in `src/` are shared with the server and imported by relative path (`src/worldBody.ts`, `src/tags.ts`, `src/preferences/generationModel.ts`, `src/preferences/language.ts`).

**Server (`server/`)** — Hono app in `index.ts` mounts `/api` (auth), `/api/worlds`, `/api/stories`, `/api/tags`, `/api/users` (profiles: `GET /:username`, `PATCH /me`). World-scoped sub-routes live in `server/routes/worlds/` (`scenes`, `generate`, `stories`, `creator-center`) and are mounted under `/:id/...` in `worlds/index.ts`. Auth is cookie-session based (`sid` httpOnly cookie → `sessions` table), enforced by `authMiddleware`. Every handler scopes by the requesting user via `route-helpers.ts`:
- `findUserWorld(userId, worldId)` — the user is the world's author. Use for anything that edits a world.
- `findVisibleWorld(userId, worldId)` — anyone's published world, or the user's own in any state. Use for reading and playing.
- `findWorldScene` — one of the author's published scenes, for a reader. (The creator center works on the draft, not rows: `server/world-draft.ts`.)

**Database (`server/db.ts`)** is the single schema source: raw `CREATE TABLE IF NOT EXISTS` DDL at the top, Drizzle table definitions below, kept in sync by hand. Not managed by Drizzle migrations. To change the schema, edit both. Ownership is enforced by `ON DELETE CASCADE` — deleting a user takes everything they own; deleting a world takes its collections, scenes, their stories, its tags links, bookmarks and changelog; deleting a scene takes every reader's stories of it.

### Entities

- **World** — one per author-written setting. No versions, no checkout. Its text is a `WorldBody` JSON document (`src/worldBody.ts`): `{ lore: [{id, title, body}], characters: [{id, name, body}], instructions }`, any number of lore sections and characters, in the author's order. Each entry's stable `id` is what lets the changelog tell an edit or rename from a delete-and-add. `renderWorldBody()` turns lore + characters into the plain text the model reads. `instructions` is one free-text block the author writes for the AI only (editor tab "For the AI"; lore and characters are "For readers"): it goes into the system prompt as its own section, is drafted/published with the rest of the body, is stripped from `GET /worlds/:id` for anyone but the author, and a publish that changes it logs a content-free `instructions_edited`.
  - **Draft vs published — the creator center's one rule: everything autosaves to the draft, and only Publish reaches readers.** `worlds.draft` is a `WorldDraft` JSON document (`src/worldDraft.ts`, shared): the world's name, blurb (the feed card's one or two lines), pairings, tags and body, plus its collections and scenes in order — the whole of what the author works on. Every creator center screen autosaves into it (`server/world-draft.ts`: `editDraft` is a read-modify-write in one transaction, so two screens' saves never clobber each other). **Publish** (`POST /worlds/:id/publish`, `publishDraft`) writes the whole draft out — `name`/`blurb`/`body` on the world row, tags and pairings to their tables, collections and scenes to theirs (updated by `row_id`, inserted when it has none, deleted when the draft dropped them) — logs the body's difference to the changelog, and stores the draft as `published_draft`; `draft != published_draft` is "changes not published" (`has_draft_changes`). Publish needs a name, every collection named and every scene finished (description and instruction); `GET /worlds/:id/draft` reports what blocks it (`publish_blocker`). Outside the creator center the author sees exactly what readers see; only the creator center reads the draft. `published` = has ever been published (visible in the feed). There is no discard: the draft is kept until published.
  - In the draft, collections and scenes are named by a `key` (the creator center's URLs) and carry the `row_id` they were published as (null until then). Readers' stories hang on scene rows, so a scene keeps its row across publishes.
  - **Pairings** (`world_pairings`; `src/pairings.ts`, shared by client and server): a fixed list — `mm`, `ff`, `mf`, `other` (EN "Pairing": MM/FF/MF/Other; ZH "性向": 男男/女女/男女/其他) — any number per world, always in the list's order. Not tags: it is Discover's primary filter (a reader's selection matches worlds with *any* of them), shown as badges ahead of the tags on cards and About.
  - **Language is the author's UI language, never chosen:** `worlds.language` is the `LanguageId` (`en`/`zh`) of the author's UI when they created the world (sent with `POST /worlds`), and never changes after. Only Discover filters by it: the feed and its tag row show just worlds in the reader's UI language. Readers and authors never see it — no label, no creator center control.
  - **Images (placeholders, no uploads yet):** `worlds.cover_url` (live, like metadata), `image_url` on each character in `WorldBody` (drafted/published with the body), and the album in `world_photos` (ordered by `position`, live). All are links meant to point at object storage later; nothing writes them yet. `src/components/WorldImages.tsx` renders the image or its fallback (tinted cover with the world's initial, the letter circle, no album section), and the creator center shows disabled "Coming soon" slots.
  - `updated_at` is the last publish — the last change a *reader* could see — never a draft save.
- **Collection** (`collections`) — the author's grouping of scenes in a world: `name`, `description`, tags, an optional `premise`, and `position` (the author's order, 0..n-1 per world). The premise is context every scene in the collection shares: `/generate` puts it in the system prompt (its own `# Premise` section) for each of them, and readers see it in full on the collection's page. Edited in the draft, published with the world (a premise edit doesn't make stories outdated). Deleting one asks whether its scenes move to "No collection" or are deleted with it (`DELETE …?scenes=move|delete`). Readers don't see empty collections.
- **Scene** (`scenes`) — the author's only, no tags, two texts: `description` (what readers see — a sneak peek / trailer of the scene) and `instruction` (what the model is given: "Write …, in this tone …"). The instruction never leaves the creator center: reader responses carry only the description, and `/generate` takes a `sceneId` and looks the instruction up server-side (a creator center test sends the scene's draft key with `draft: true`, and the server plays it from the draft). In one collection or none (`collection_id` null: the "No collection" group, shown last), at `position` 0..n-1 within its group; positions written out on each publish. Edited in the draft like everything else; a deleted scene (and readers' stories of it) goes on the next publish. `updated_at` moves only when a publish changes the instruction — that is what makes readers' earlier stories outdated — never on a description edit or a move.
- **Story** — a reader's saved generation of a scene (`scene_id`, cascade). Always private. Generated text is held in the client until the reader saves it; unsaved generations never reach this table. **Outdated** = `scene.updated_at > story.created_at` (its instruction changed): it still reads and is marked in the story strip. For now it can still be resumed like any other story (the greyed-out Resume and the server's 409 are commented out in `ScenePage.tsx` and `server/routes/stories.ts`).
- **Tags** — one global, freeform vocabulary shared by worlds and collections (`tags`, `world_tags`, `collection_tags`). `normalizeTag()` in `src/tags.ts` is the one place two spellings become the same tag (NFKC, case-fold, `-`/`_`/whitespace → one space, leading `#` dropped); client and server both use it, and `tags.name` stores the normalized form. Tag order on an item is the order typed. Autocomplete (`GET /api/tags?q=`) offers existing tags most-used first so the same idea converges on one spelling. Character names are deliberately *not* auto-offered as tags — one lead appears in nearly every scene, so they carry no signal.
- **Generations** — one row per generation run, saved or not, with the words streamed (characters for Chinese). This is the **popularity signal**: total words, plus distinct readers, per world and per scene. `scene_id` is `SET NULL` on delete so a removed scene keeps counting toward its world.
- **Bookmarks** — (reader, world), public: they make up the Bookmarked tab of the reader's profile. Nobody can bookmark their own world (the server refuses).
- **User** — `username` and a `bio` (shown on their profile). No avatar yet: a letter circle stands in until the app has pictures.
- **World changes** — the auto-generated changelog. `kind` is a fixed code (`WorldChangeKind` in `src/worldBody.ts`: `published`, `lore_added|edited|renamed|removed`, `character_…`, `instructions_edited`) and `label` names the thing (a rename's label is `old → new`), so the client renders the sentence in the reader's language (`worldChangeSentence` in `i18n.ts`). Produced by `diffWorldBodies()` in `server/world-changes.ts` on publish. It records world changes only — never scenes.

### Generation flow

Server-sent events end to end:
- Client `src/hooks/useGeneration.ts` is a reducer-based state machine (`idle → waiting_provider → thinking → writing`). It POSTs to `/api/worlds/:id/generate`, reads the SSE stream via `src/utils/sse.ts`, and appends `chunk` events into an `output` buffer. Each run gets a client-generated `generationId` and its own `AbortController`; a replacing run (e.g. "expand") aborts the prior one and stays silent.
- Server `server/routes/worlds/generate.ts` builds the system prompt from the world's rendered body, proxies to OpenRouter's streaming chat completions, and re-emits typed SSE events (`status`, `provider`, `thinking`, `chunk`, `error`, `done`). Everyone generates from what was published, the author included, except a creator center test run (`draft: true` in the request, honored for the author only), which plays the scene, its collection's premise and the world body from the draft. Test runs are scratch: never saved, and they should not count toward popularity. The route's `finally` (which runs on done, stop, replacement and disconnect alike) is where the run's word count is written to `generations`.
- **`server/generation-lock.ts` is the hard guarantee that only ONE OpenRouter session runs at a time, process-wide** — the account allows a single concurrent session and overlap gets the whole key 429'd. `withGenerationSlot` is a promise-chain mutex (call N+1 never opens its socket until N has drained, plus a settle delay for OpenRouter to free its slot); `registerGeneration`/`abortGeneration` key runs by owner (`userId:worldId`) so a user's new action (or `POST /generate/stop`, or a client disconnect) aborts and drains their prior run first. The `/generate` route gets an unbounded server timeout (set in `index.ts`).
- Expand / Continue / Resume stay: "Expand" resends prior text as an assistant turn plus an instruction to elaborate the last paragraph; "Resume" reopens a saved story, continues it, and PATCHes it in place.

> **Not built yet:** writing each run's word count to `generations` (the `finally` described above). Until it lands, `generations` stays empty and every popularity count reads zero.

**Size limits live at the model call, nowhere else (`server/llm-budget.ts`).** Every OpenRouter chat body goes through `budgeted()`, which caps output tokens and warns (without editing) when the input has outgrown the budget. Nothing upstream truncates a world body or a scene — half a premise is a wrong premise, not a smaller one. When a caller has more material than it wants to send, that is a ranking decision in SQL, not a slice.

**Models are a shared source of truth.** `src/preferences/generationModel.ts` defines the `MODELS` array and `BLACKLISTED_PROVIDERS` — imported by **both** client and server. Add or change a model in this one file.

### Client

`src/App.tsx` defines all routes under a `ProtectedLayout`. It deliberately uses `createBrowserRouter` (data router) so the reading view can `useBlocker`/`useUnsavedExitGuard` to guard against losing unsaved generated text on back/swipe.

- `/` **Discover** (`src/pages/home/`) — the home page, no tabs. The public feed, only worlds in the reader's UI language: search, sort (popular/new), a row of pairing chips (the primary filter), then a sideways-scrolling row of tag pills; search, sort, selected pairings and tags live in the URL.
- **The reading side never knows about the creator center.** An author sees their own world as any reader does — no Creator center button, no publish state — except that "Your world" stands where readers have Bookmark. The menu (top-right person icon: Your profile, Creator center) is the only way into the creator center. Discover is the Home icon at the top left of every screen (after Back, when there is one) except inside a world's creator center (`/worlds/:id/edit…`), which has none: it is left by Back, to `/creator-center`.
- `/u/:username` **Profile** (`src/pages/profile/`) — the same for everyone: the profile card (letter circle, name, bio), then under it two tabs (sticky under the top bar on scroll), **Created** (`/u/:username`, their published worlds) and **Bookmarked** (`/u/:username/bookmarked`), as normal cards opening the read-only world page. There is no separate Library: your bookmarks are your profile's Bookmarked tab. Reached from the Author card on About (which passes `state.from` so Back returns there; `TabBar` carries router state across `replace` tab switches) or from the menu (top level, no Back). The owner gets Edit profile → `/profile/edit` (bio, autosaved).
- `/worlds/:id` **About** (first tab, where a world card lands) and `/worlds/:id/scenes` **Scenes** — the world's two tabs (`WorldTabs`; the old `/about` URL redirects). About is identical for everyone: the action row (Bookmark, or "Your world" for its author), the intro card (name, blurb, tags, metadata, Update history link), the Author card (letter circle, name, published-world count → profile), lore sections, characters. Scenes: one section per collection in the author's order (name → its page, description, a "Has premise" chip, tags, then its first 3 scene cards and See all), "No collection" last with all its scenes; the tag pills filter collections (and hide No collection while a tag is on).
- `/worlds/:id/collections/:collectionId` — `WorldCollection`, the reader's collection page: name, description, tags, the premise in full, every scene. Built from the `['world-scenes', id]` data. A scene page's Back goes here when the scene is in a collection, else to the Scenes tab.
- **Creator center** (shown to users as "Creator center" / 作者中心; `src/pages/creator-center/`, author only; every screen autosaves to the world's draft via `useAutosave`, which retries a failed save while the screen is open) — a separate place, the only one where the author works on their world, and it never links out to the reading side. The World and Scenes tabs share one header, `CreatorWorldHeader`: the title "Edit · <the draft's world name>" (centered, no subtitle), then `CreatorStatusBar` above the tabs (it acts on the whole world), then the tabs. The status bar (a scene or collection page has only `CreatorSaveLine` — Saving… / Saved / Couldn't save, nothing before the first change — since Publish is the whole world's, it never sits on a page about one part): Publish on the left (publishes the whole world, after flushing the screen's autosave) and one sentence — Saving…, Couldn't save · retrying (red), what blocks publishing (counted, e.g. Finish 2 scenes to publish, linking to the Scenes tab from elsewhere), Not published yet / Changes not published, or Published · up to date. `/creator-center` (`CreatorCenterHome`, from the menu): the author's worlds in any state, as their drafts have them (`GET /worlds/mine`), each card saying whether changes aren't published, and New world. **New world, New collection and New scene open an empty editor at `…/new` that is stored nowhere until something is typed**: the first save creates the item (`POST`) and replaces the URL with its id or key, so opening one and backing out leaves nothing behind. Inside a world's creator center the top bar's title is "Edit · <name>" (`useCreatorTitle`), with the draft's name, not the published one. Back inside the creator center goes scene → Scenes tab → `/creator-center`. A world has two tabs (`CreatorTabs`): `/worlds/:id/edit` **World** (`CreatorWorld`: a *For readers* group — name, blurb, pairing, tags, lore, characters — and a *For the AI* group — instructions; Delete at the bottom) and `/worlds/:id/edit/scenes` **Scenes** (`CreatorScenes`: collections in order, each with its scenes (Unfinished marked) and New scene, then No collection; FAB New collection; a **Reorder** mode swaps every row for up/down arrows plus a collection picker on each scene). `/worlds/:id/edit/collections/:collectionId` (`CreatorCollectionPage`): name, description, tags, premise (autosaved), its scenes, New scene, Delete with the move-or-delete choice. `/worlds/:id/edit/scenes/:sceneId` (`CreatorScenePage`): Description, Instruction for the AI, and a `CollectionPicker` chip (moves it in the draft), then Test (+ model picker); Delete is the trash icon in the top bar. `/…/test` (`CreatorTestScreen`): the streaming reader playing the scene as saved in the draft (the editor flushes first), with its collection's premise and the world draft, no save. Server side: `server/routes/worlds/creator-center.ts`, and `GET /worlds/:id/draft`.
- `/worlds/:id/changes` — the changelog.
- `/worlds/:id/scenes/:sceneId` — `ScenePage`: the scene (its collection's name above it), Generate, the reader's saved stories (outdated ones marked, Resume greyed out); `/generate` is the streaming reader (Expand / Continue / Resume, save or discard).

Shared response types are in `src/pages/worlds/shared/worldTypes.ts`. Query keys: `['feed', language, q, pairings, tags, sort]`, `['profile', username]`, `['creator-worlds']`, `['world', id]`, `['world-scenes', id]`, `['scene', id, sceneId, limit]`, `['creator-collections', id]`, `['creator-collection', id, collectionId]`, `['creator-scene', id, sceneId]` (`invalidateWorldScenes` in `creator-center/creatorQueries.ts` refreshes all of them after a creator center change), `['world-changes', id]`, `['tags', q]` (Discover's tag row: `['tags', '', language]`).

**Preferences** (`src/preferences/`) are localStorage-backed reactive stores built with `createPreference.ts` (via `useSyncExternalStore`) — model choice, language, reading font/size/speed, theme. Not server state.

**i18n** — `src/i18n.ts` plus a `language` preference; the app is bilingual (English / Chinese `zh`). Every key must exist in both the `en` and `zh` tables (the `UiText` type is their union). The UI and the code use the same entity words — world, collection, scene, story, creator center (设定集/合集/场景/故事/作者中心) — and there is no label map between them: each sentence is its own i18n key, counts included (`sceneCount(n)`, `storyCount(n)`). "Take" is not a word the app uses; the buttons say Generate / Generate again. "Prompt" in the code means only an LLM prompt (the system prompt, `server/prompt-text.ts`). Several formatters branch on language and on whether text contains Chinese characters (word vs. character counts); popularity counts use `formatCompact` (`12K` / `1.2万`).

## Conventions

- **Mobile-only, touch app.** No hover/focus affordance styles — use resting weight and `active:` press states.
